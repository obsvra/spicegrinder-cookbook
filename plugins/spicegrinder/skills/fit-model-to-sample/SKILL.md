# Fit Model to Sample

## Overview

A user provides sample data and wants to determine how to generate similar data using SpiceGrinder. This skill turns a real data sample into a working SpiceGrinder model by fitting each column to the closest available generator, filter, or business object, then composing the pieces into a model definition.

## When to Use

Upon user request, or when the user has real sample data at hand but is unsure how to model it in SpiceGrinder.

## Instructions

1) **Ground yourself in the real component catalog before fitting anything.** Every recommendation this skill makes has to name a component that actually exists, with the actual parameters that component takes -- guessing a plausible-sounding generator name is worse than useless, since it produces a model that won't load. Read `docs/Component-Library-Reference.md` from the user's SpiceGrinder repo checkout (check your memory for the configured default location first) for the authoritative, auto-generated list of every generator, filter, and business object, its real parameters, and its Free/Pro tier. If that repo can't be found at the expected path, ask the user where their checkout lives before falling back to the bundled snapshot at `references/component-catalog.md` -- and if you do fall back to it, tell the user explicitly that it's a point-in-time copy and may be missing components added since (this project ships new business objects frequently). If no SpiceGrinder installation can be found at all -- no repo checkout, no packaged app, nothing beyond this skill's own bundle -- say so and point the user to https://obsvra.com/get-spicegrinder; the bundled snapshot still lets this skill produce a fitted draft, but nothing has validated or run that draft against a real install yet. While reading the catalog, note each candidate's tier: unless the user has confirmed they have Pro-tier access, prefer a Free-tier match and only recommend a Pro-only component when no Free-tier equivalent exists, explaining why the Pro-only one is necessary.

2) **Fit each column statistically, don't eyeball it.** For each independent subset of the data (e.g. each column in a CSV), compute summary statistics -- mean, variance, skewness, discreteness, cardinality -- and test candidate distributions against the data with a Python script (a KS test or AIC/BIC comparison across candidates). "Best fit" means the distribution the data actually supports, not a guess from looking at a few rows. **Before fitting any numeric column, count its most frequent exact values.** A single value holding a notable share of the rows (say 1% or more) is a spike, and a continuous distribution will never produce it -- no matter where it sits in the range. Spikes inside the bulk of the data are easy to miss because they don't look like outliers: a default a system records when the real value is unknown (a form that fills in 30 minutes when nobody enters a duration), a fixed or list price (a subscription at 9.99), quantities people choose in round or standard amounts (ages reported as 40, 45, 50; order sizes of 10 or 100), exact zeros. Model each spike as a `Constant` inside a `Mix` with the continuous fit, weighted by its observed share, and fit the continuous part to the remaining rows only. For an integer-valued column whose rows concentrate on a handful of values, skip the continuous fit altogether and use a weighted set of those values. **Watch for a spike at a floor that is really the start of a discrete stretch.** Counts often start at a floor: a suppression threshold (CMS publishes no row with fewer than 11 beneficiaries), a minimum order. If the values just above the floor are also frequent whole numbers (11, 12, 13... each holding several percent), a `Constant` at the floor only moves the mismatch to the next value, because the continuous part spreads its mass between the integers. Check the next few values after placing a spike. If they're frequent too, model the whole near-floor stretch as one weighted set of those values (the popular-value grid below), up to where the counts thin out, with the continuous fit for the rest. Round the continuous part to whole numbers too.

   **Popular-value grids (limited numeric replay).** Some measurement columns sit on a grid of popular exact values rather than spreading smoothly: fares and prices (standard fares, list prices, whole dollars), magnitudes recorded to 0.1, quantities sold in pack sizes. A continuous fit can't produce those exact values. When the repeated values in such a column together cover a large share of its rows, model the popular ones the way spikes are modeled: one `Empirical` holding each value that appears in at least 0.2% of the rows and at least 10 times, weighted by its observed share, inside a `Mix` with the continuous fit for the remaining rows. Round the continuous part to the data's own precision with `Calculate` (`y[0] = round(x[0] * 100) / 100` for cents). This copies real values into the model, so it is allowed only under all of these rules:
   - **Purely numeric measurements only:** amounts, prices, counts, durations, sizes, physical readings.
   - **Never anything that could even remotely be PII:** no identifiers of any kind (account, phone, ZIP or postal, NPI, SSN, member or claim numbers, even when they look like plain numbers), no dates or times, no ages or other attributes of a person, no free text. When in doubt, don't replay; fit the column instead, and use the `pii-audit` skill if the sample may hold personal data.
   - **Classification codes are categories, not identifiers:** a code that names a *kind* of thing shared by many records -- a procedure code (HCPCS, CPT), a provider specialty, a product category, a diagnosis group -- identifies no one, so its observed values and frequencies may go in a `Categorical` or weighted table like any other category (step 4). The test is whether a value points to one person, account or place; a code that does (a member ID, a device serial) is an identifier, whatever it's called.
   - **Popular values only:** never a value below those thresholds, so a rare value that could single out a record never reaches the model.
   - **Say so in your notes:** list every column you replayed, how many values, what share of rows they cover, and why the column is safe to replay.

   **Heavy tails: splice a body and a tail.** Some columns have a bulk that one distribution fits well and a long right tail that it doesn't: payments, charges, counts per provider, claim sizes, file sizes. Fitting a single `Lognormal` or `Pareto` to the whole column forces a trade: fit the bulk (maximum likelihood, good KS) and the p95/p99 come out far off, or match the tail quantiles and the bulk KS gets worse. Splice instead, so each part is fitted only to its own region:
   - **Choose a threshold `u`** where the tail starts: where a log-log plot of the largest values (log of value against log of the fraction of rows at or above it) turns into a straight line, or failing that the 90th-95th percentile. Keep at least about 100 rows above `u`.
   - **Body:** fit a distribution (`Lognormal`, `Gamma`, `Weibull`) to the rows below `u` only, and cap it at `u` with `Truncate` (`max` = `u`, the default `truncate` mode, which redraws rather than piling values at `u`).
   - **Tail:** fit a `Pareto` with `scale` = `u` to the rows above `u` only. Its `shape` by maximum likelihood is `n / sum(log(x / u))` over those n rows; a shape at or below 2 means the tail is heavy enough that its variance is effectively unbounded, so check the output's largest values against the sample's.
   - **Join them** with a `Mix` weighted by the observed shares below and above `u`.
   - **Integer counts:** round the result (`Calculate` or `ToInteger`), and if the column has a hard minimum (a suppression floor, such as counts under 11 never appearing), set the body's `Truncate` `min` to it.

   The spliced column is still a distribution, so it can be a `Copula` input (step 3). Check it with `compare` like any other: the tail percentiles should now be close without the KS getting worse.

**Before step 3: entities repeated across rows.** In transactional data the same entity appears on several rows: a provider on each service billed, a customer on each order, a vehicle on each trip. Find it before fitting anything else, because it changes what the other steps fit:
   - **Detect it:** for each identifier or address column (many distinct values), count the rows per value. If values repeat (a column with far fewer distinct values than rows: `compare`'s `repetition` check flags a model that misses this), the table has entities.
   - **Split the columns** into entity-level ones, which never change within one identifier (the identity, the address, a specialty: check that each takes one value per identifier), and row-level ones, which do (the service, the amount).
   - **Build the entity** under a `Pool`: its `entity` input generates the entity-level columns (business objects for identity and address; the same privacy rules as always), and its `count` input is the number of rows per entity, fitted from the sample's rows per identifier (an `Empirical` of how many identifiers have 1, 2, 3... rows: counts, not identity data). Set `interleave` to 1 if the sample's rows for one entity sit together, or to a few hundred if they're spread through the file. Join the row-level columns with `Append`.
   - **Check whether the number of rows depends on the entity.** Compare the mean rows per identifier across the values of each entity-level category (specialty, customer segment). If they differ (one specialty averages 15 rows per provider, another 1), a single `count` gets the per-row shares of that category wrong, because every entity gets the average number of rows. Instead, make the count one of the entity's own columns: append a `Switch` keyed on the category, with one rows-per-identifier `Empirical` per value that differs enough to matter and has at least 10 entities (see the next bullet), and a `value="*"` branch for the rest, and give the `Pool` only the entity input and `countColumn` = that column (it isn't passed on).
   - **At least 10 real entities behind anything that depends on the entity.** Each entity-level column can be safe on its own (a specialty is a classification code, a row count is a number) while the combination is a profile: the only organization of a rare specialty with 57 rows is one real provider, name or not. So every table or branch that ties values to an entity must be built from at least 10 of the sample's entities:
     - A branch per category (a `Switch` branch with its own count `Empirical`) only for a category with at least 10 entities; smaller categories share the `value="*"` branch, fitted over all of them together.
     - A table of whole entity profiles, drawn instead of fitting (one row per combination of specialty, rows and organization flag), only holds combinations that at least 10 sample entities share, weighted by how many share each; never one row per real entity. Group row counts into ranges first (1, 2, 3-4, 5-6, 7-8, 9-12, 13-16, 17-24, ...) so more combinations qualify, and draw the exact count within the range from the fitted count distribution. The entities in rarer combinations come from the fitted path (category from its weighted table, count from its `Switch` branch), in a `Mix` weighted by the share of entities each path covers.
     - 10 matches the popular-value minimum above; CMS applies 11 to its own published Medicare cells. In your notes, say how many entities and rows the replayed profiles cover and how many came from the fitted path. Accuracy on rare groups is what this costs, and it's the intended trade.
   - **Fit entity-level columns over one row per entity,** not per row: otherwise an entity with 50 rows counts 50 times in, say, the specialty distribution. Row-level columns are fitted over all rows as usual (steps 2-3).
   - **Row-level columns that depend on an entity attribute** (a cardiologist bills cardiology procedures at cardiology prices): check whether their distributions differ by the attribute's value, and if they do, use `Switch` with `key` = that attribute's column, one branch per value that differs enough to matter and a `value="*"` branch for the rest. The same applies to any category that changes the shape of other columns (a payment type that decides whether there's a tip): `Switch` routes on the category's value instead of generating every column inside separate `Mix` branches, which keeps models smaller and the category's own distribution in one place.

3) **Check numeric columns for correlation before fitting them independently.** Two or more numeric columns that are genuinely correlated (e.g. height and weight, or any pair with real covariance) lose that relationship if modeled as independent per-column distributions -- the synthetic data would look right column-by-column but fall apart the moment someone checks the relationship between them. Compute pairwise correlation (or a full covariance matrix for more than two columns) across the numeric columns before committing to independent fits. Where a real correlation exists, keep it. When the columns are roughly jointly normal, use SpiceGrinder's `MultivariateNormal` generator. When they are skewed, bounded or discrete (the usual case), use `Copula`: fit each column on its own as in step 2 (any univariate generator, including a `Mix`, a `Truncate` or an `Empirical`, and a `Calculate` that shifts, scales or negates one, such as a Gamma tail starting at 5 with `y[0] = x[0] + 5` or returns as `y[0] = -x[0]`; any other `Calculate`, including `round()`, can't be a `Copula` input, so round after the `Copula` instead), wire those fits in as the `Copula`'s inputs, and give it a `correlation` matrix. Measure the rank (Spearman) correlation `rs` for each pair, since it doesn't depend on each column's shape, and convert it with `r = 2 sin(pi rs / 6)`. If the columns' extremes happen together (the largest values in one column tend to come in the same rows as the largest in the other, more often than the correlation alone explains), add `df` (try 3 to 10) for a Student-t copula. If `Copula` rejects the matrix as not positive definite, the pairwise estimates are inconsistent; shrink the off-diagonal values slightly toward 0 until it loads. When one column follows another along a curve that rises and then falls (or otherwise changes direction), which no correlation expresses, derive it with `Calculate` (a regression) plus noise fitted to the residuals instead. Also check for hard rules between columns, which correlation alone won't reproduce: one column never below another (items shipped never exceed items ordered), a ratio that stays in a fixed range, or a total that equals the sum of its parts. When a rule holds in every row, build it into the model: generate one column, then derive the other from it with `Calculate` (for example, the smaller column times a factor of at least 1). A correlated pair only follows the rule most of the time.

4) **Check for a business-object shape match before falling back to value-replay.** A column with no good statistical fit doesn't automatically mean "sample from the values I found" -- that's a real risk, not a neutral fallback. If a column's format matches an existing business object's output shape (e.g. `XXX-XX-XXXX` -> `SSN`, an 8-hex-group colon-separated string -> `MACAddress`, an `@domain`-shaped string -> `Email`), recommend that business object instead (cross-checked against the catalog from step 1 -- don't recommend a business object that isn't actually in it). Only fall back to a value-replay distribution (a Categorical/Empirical built from the observed values themselves) when no business object or generator fits *and* the column is confirmed non-identifying. Never replay real SSNs, names, emails, or other identifying values verbatim into a "synthetic" model -- that isn't synthetic data, it's the original data with extra steps, and it defeats the reason these business objects exist. Match on what a column contains, not on a single component name. Some business objects build a whole composite value: `Address` produces one address (house number, street, optional unit, city, state, ZIP, mutually consistent) and `PersonAssembler` one name from gender, given name and surname sources. Each emits that value as a single output, printed whole (`2607 Chestnut St, Woodville, VA 22749`), so it fits a sample that holds the whole address or name in one column. When the sample spreads it across separate columns (street, city, state, ZIP), follow it with `Extract` (Pro), which replaces the composite with the fields you name, one column each, in place: for example `fields="streetLine,city,region,postalCode"` for an address (`streetLine` is number, street and unit together; `postalCode` stays text, leading zeros kept) or `fields="givenName,surname"` for a name. The catalog lists each business object's fields; `formatted` keeps the whole value as well. Use `Arrange` to put the resulting columns in the sample's order. `NPI`, `Phone`, `Email`, `SSN`, `EIN`, `RoutingNumber`, `CreditCard`, `IBAN` and `VIN` each produce valid identifiers of their kind. Before concluding "no component builds this", search the catalog's descriptions for the column's content.

   **Use the largest bundled reference table for each source.** Business objects draw from reference tables, and some come in two sizes: the given-name and surname lists ship as 100-entry unweighted files (`samples/pro/surnames.csv`, `male_names.csv`, `female_names.csv`, for small demos) and as 1,000-entry files weighted by real frequency (`surnames_weighted.csv`, `male_names_weighted.csv`, `female_names_weighted.csv`, used by `samples/pro/person-name-usa-*.xml`). Use the weighted ones, with `mode="weighted"`. With 100 names, a column of 5,000 rows can't have more than 100 distinct values; the Medicare evaluation's model got 166 distinct last names in 5,000 rows against 1,048 in as many real rows, and `compare` flagged it as high. Even 1,000 names fall short of a real population (569 against 1,048 in the same evaluation), so list it under limitations. Real names aren't an option for closing the gap. Before picking any bundled file, list `samples/pro/` and compare the files' header comments.

5) **Consider mixtures.** A column that resists a single clean distributional fit may actually be several distinct sub-populations mixed together (e.g. two customer segments with different purchase-amount distributions). Check whether splitting the data (by another column, or by a bimodal/multimodal shape in the fit itself) produces cleaner per-group fits before concluding the column just doesn't fit anything. The same holds for groups of columns: points that clump into a few separate clusters (earthquake locations along fault lines, delivery addresses around depots) are a `Mix` of several `MultivariateNormal`s, one per cluster, not one wide normal.

   Search for sub-populations with a floor and a ceiling, so the search is thorough enough without running away:
   - **Floor (always check):** for every column that fails a single fit, try splitting it by each categorical column with about 20 or fewer values, and try a two- and three-part mixture on the column itself. For each correlated group of columns from step 3, check whether the points clump into clusters.
   - **Ceiling (stop here):** split at most two levels deep (split once, then split one resulting group once more, no further). Use no more than about 5 parts per mixture. Give each part at least 5% of the rows (and no fewer than about 100 rows), because smaller groups fit noise. Keep a split only if the parts fit clearly better than the whole did (a lower KS statistic or a better information criterion such as BIC), and stop when another split stops helping.
   - In your notes, list the splits you tried and why you stopped, so the user can go further by hand.

6) **Look for patterned outliers -> perturbation, not a second mixture.** After accounting for mixtures in step 5 and spikes in step 2 (exact repeated values are spikes, handled there, not perturbation), examine what's left. If the remaining outliers follow a describable, consistent pattern relative to the base distribution (e.g. a fixed offset, a scaled variant, systematic noise around an otherwise-clean fit), that's a signal for SpiceGrinder's perturbation filter (`Perturb`) wrapping the base generator -- not a new, separate mixture component. Reserve `Mix` for genuinely distinct sub-populations (step 5) and `Perturb` for structured noise on top of one.

7) **Compose the model.** Once a best fit is established for every column, use the `build-spicegrinder-model` skill to turn the fitted pieces into an actual SpiceGrinder model definition. Don't hand-roll the XML/JSON here -- that's what the sibling skill is for.

8) **Check what the model actually produces before handing it over.** Run SpiceGrinder's `compare` tool on the model and the sample (`compare --seed 1 model.xml sample.csv`, from the folder the model's data paths are relative to; `--json` for a report you can parse). It generates as many rows as the sample has and checks each column: the format of the values, the share of every frequent exact value (the spikes from step 2), distributions and tail percentiles (judged against sampling noise), category frequencies, identifier values copied from the sample, and the correlations from step 3. Exit code 1 means a high-severity difference. Fix what it reports and run it again; include its final report with the model, so the user gets measured evidence alongside your notes, not only your account of the fit. If `compare` isn't available (an older SpiceGrinder), generate a few thousand rows with `Grind` and make the same comparisons with code rather than by eye. Format is the easiest to get wrong and the hardest to spot: a postal code written as `12345.0`, an account number like `00731` that lost its leading zeros, or a code with letters in it (`AB12`) that a numeric generator can't produce at all. Identifier-like columns -- ZIP codes, product or procedure codes, account numbers, anything with leading zeros or letters -- must be generated as text, not numbers (string values are Pro-only; on Free, tell the user such a column can't be reproduced faithfully). A reference table read with `FlatFile` needs those columns listed in its `textColumns` parameter (0-based indexes, or header names with `skipHeader="true"`). Otherwise any cell that looks like a number is read as one, quoted or not, and a ZIP comes back as `2134.0`. Whole numbers need the same care: numbers read from a table, and most generator output, print with a decimal point, so a count, a quantity or an ID that is `12` in the sample comes out as `12.0` unless the chain ends in `ToInteger` (`mode="round"`, with `indexes` naming just those columns). Match the sample's form exactly (decimal places included): the closer the output is to the source, the better. Also check that every spike from step 2 still has its share in the output: a later filter in the chain can shift an exact value off its spike. Fix what the comparison shows, then compare again. Then go through `references/review-guide.md` (the same guide users get): it lists what `compare` can't judge, including repeated entities, extreme tails, unexplained spikes, rules between columns and small groups. Use it both to check your own model and to write the "what a user should review by hand" part of your notes, specific to this model. If no SpiceGrinder is installed (the situation step 1 describes), you can't run this check or the `Grind` fallback: say plainly that the fit has not been checked against the sample, give the user the `compare` command to run once SpiceGrinder is installed, and don't present your own estimate of how well it matches as a measured result.

## Output Format

Output a candidate SpiceGrinder model file in the user's preferred format (default to XML if the preferred format is unknown).
