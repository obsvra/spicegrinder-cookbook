# Pattern map: system features to SpiceGrinder primitives

Used in steps 1 and 3 of `create-spicegrinder-simulation`. Always confirm component names, parameters and tiers in the catalog; this file says which primitive to reach for, not what its attributes are. Worked examples are in `samples/simulation/` (Free) and `samples/pro/` (Pro), and in the Simulation 101 lessons under `learn/`.

## The decision that comes first: what is a row?

SpiceGrinder is pull-based and each output row is one unit of the run. Everything else follows from the choice.

| Row is | Use when | Primitives | Time |
|---|---|---|---|
| A **time step** (a day, a month) | Stock, cash, backlog, fixed-cycle policies, continuous quantities approximated in steps | `Recur`, `SharedState` | Implicit: row n is step n. Shorter steps cost more rows. |
| A **customer** | One server or a short line of servers, first come first served, the questions are per customer | `Recur` (Lindley or departure-time recursions: `Recur-Patterns.md` in `references/`) | A column you compute; no clock |
| A **time step**, with a hand-built queue and resource model | Anything `ProcessFlow` cannot express (preemption, ageing, vehicle rules of your own, positions inside a batch), at a step short against the service times | `SharedState` plus `Calculate` nodes whose shared values are `let` locals (see "Slot models" below) | Implicit: row n is step n; cost grows with the number of steps |
| An **event** or a **departed entity** | Queueing networks: several stations, parallel servers, routing, utilization over time | `ProcessFlow` (Pro) | A clock column, uneven spacing; `output="entities"` gives one row per customer |
| A **path** | Many independent replications of a short horizon in one run | `Recur` with `resetEvery`, then `Redimension` | Block of rows per path |

Do not mix row definitions without a reason: state kept on a time-step row cannot see events that happen between steps.

## Features and the primitive that expresses them

| System feature | Primitive | Notes and limits |
|---|---|---|
| Random inputs (demand, durations, gaps) | The distribution generators (`Poisson`, `NegativeBinomial`, `Exponential`, `Gamma`, `Lognormal`, `Weibull`, `Empirical`, `Categorical`) | Pick from the catalog by the shape of the quantity: counts, positive skewed durations, bounded values. Overdispersed counts: `NegativeBinomial`, not `Poisson`. |
| Related random inputs | `Copula` (any marginals, a correlation matrix), `MultivariateNormal` | Correlated demand across stores, duration with size |
| Mixed populations / regimes | `Mix`; `Markov` for regimes that persist (busy/quiet, healthy/broken) | A `Mix` redraws each row; a `Markov` chain remembers. `Markov` holding times are geometric; other durations pair it with `Pool`. |
| Category-dependent behaviour | `Switch` keyed on a category column | One branch per category; every branch has the same number of columns |
| Entities repeated across rows | `Pool` | Entity-level attributes drawn once, the row count per entity |
| A balance carried over time (cash, backlog, queue wait) | `Recur` | State columns `s[i]`, input `x[i]`; assignments read only the previous state. A response that must land in the same row belongs here (or in one `Calculate`), not in `SharedState`. |
| Stock, capacity, or any number that separate parts of the model read and write | `SharedState` with `StateRead` and `StateWrite` (Pro) | Reads see the end of the previous row; every loop has a one-row delay. A cell has at most one `set` writer plus any number of `add` writers. A pipeline of delays (a 3-day lead time) is more cells, one per day in the pipe. |
| A reaction rule (reorder when stock is low, reprice, throttle) | `Calculate` over `StateRead` values, written back with `StateWrite` | State the rule's inputs and their age. A threshold on a one-row-old stock is a different system from one on today's. |
| Queueing network: stations, parallel identical servers, probabilistic routing, FIFO | `ProcessFlow` (Pro) | See below |
| Several copies of the same unit (stores, machines) | A library file with `declare` parameters, `Import`ed once per unit (Pro) | Each import gets its own store and its own random streams. Do not copy-paste nodes. |
| A lever the user will vary | `declare` (Pro), or a named `Constant` | Everything the what-if questions touch |
| A rule that lives outside SpiceGrinder (an existing pricing service) | `ServiceCall` (Pro) | The address must be on the operator's allow-list; not in the golden-output gate, so say it needs the service running |
| A slow random quantity on a fast step (a daily weather draw held over 24 hourly rows, a regime that changes at midnight) | A `Recur` that refreshes its state only when the step counter says so: `if(mod(h, 24) == 0, new draw, s[k])`, with the draws in its input | Per-node streams fix the draw order; check that the held value changes only at the boundary |
| A continuous profile by time of day or season (solar, temperature, a load shape) | `Profile` (one node: the value of a `time:value` profile at each step, step or linear, repeating, with a second profile for a year shape, `scale` and `offset`), times a random level in a `Calculate` when the level is random; `interp(x, x0,y0, x1,y1, ...)` and `lookup(...)` read a table from a clock column; `RateSchedule` is for event counts only | State the shape and its source as an assumption |
| Stock that expires (perishable goods, batches with a shelf life) | One `Recur` with one state cell per remaining-life class; sell the oldest first, shift the cells each step, and report what falls off the end as expired | Check units in = units sold + expired + on hand; a shelf life that is a lever must not exceed the number of cells (a declare has no range check) |
| Orders or shipments in flight with variable lead times | State cells indexed by arrival step (one cell per possible delay), written when the order is placed and read when the step reaches it | Several orders can be in flight; decide whether the reorder trigger counts them (inventory position) or only on-hand stock, since that choice can change the result more than the levers |
| A count among N individuals where N (or the probability) is state (survivors, defects, arrivals in a step), or any draw whose parameters follow the model (a seasonal mean) | `Draw distribution="Binomial" params="n = x[0]; p = x[1]"` over the input columns (any scalar distribution of the library; `lambda = ...`, `mean = ..., sigma = ...`); a Normal approximation is wrong at small N, where extinction and stockouts happen | A standard `Binomial` costs one uniform per trial, so a very large N is slow; say which approximation you used if you used one. `Draw` takes its state from its input, so a state read from `SharedState` is one row behind, and a `Recur` cannot feed it in the same row |
| A probability of an event (extinction, stockout, ruin) | One run with many independent paths: `resetEvery` on the `Recur` that holds the state, a latched flag column set when the event happens, and `50 x R` rows for R replications; report the fraction of paths with the flag set with a Wilson interval | A rare event needs many paths: size R from the interval width you need, and say how many you ran |
| A stock with a capacity and limited flow in and out (battery, tank, buffer, cash with an overdraft limit) | One `Recur` whose state is the stored amount, so the response lands in the same step; clamp the state to its bounds | Check conservation, the bounds and the extremes; clamp floating-point drift |
| Seasonal or time-of-day rates | A time-step model: `RateSchedule` (one node: the number of events per step from `time:rate` points, step or linear, optionally repeating, `scale` as the lever). A `ProcessFlow` model: its `rate` option (the same points; the `arrival` input becomes an `Exponential` of rate 1) | Exact: the mean of each step is the integral of the rate. Check arrivals per hour against the integral. |
| Time-weighted averages (queue length over event time) | A `Recur` with area, previous time, previous value as state | Event rows are unevenly spaced, so the mean over rows is wrong: a queue length that lasts a long time and one that lasts an instant each count once. Weight each value by how long it lasted: the sum of value x (next time - this time), divided by the total time. State columns: the running area, the previous time, the previous value. |

## ProcessFlow in short

A Pro filter that runs an event calendar inside one node. Stations are `Name:servers` pairs, `entry` says where arrivals go, `routing` is `From>To:prob` edges with `exit` as the way out. The arrival gap and each station's service time are ordinary input nodes with roles (`arrival`, `service.<Station>`), so any distribution, `Empirical` table or fitted model can drive it. Arrivals that vary with the clock use the `rate` option (`time:rate` points, step or linear, optionally repeating); the arrival input is then an `Exponential` of rate 1 for a Poisson stream. `output="events"` (default) gives one row per event (time, entity, station, type, queue, busy, in-system); `output="entities"` gives one row per departed customer (exit time, entity, time in system, total wait, total service, visits), which is what most per-customer questions need. Time is dimensionless. Confirm attribute names against the catalog entry.

Use it when the system is a queueing network: arrivals, stations with a number of identical servers each, FIFO, and probabilistic routing. Model it like this:
- one `ProcessFlow`, one station per physical stage, `servers` from the real count; the number of servers is a lever (`declare`);
- the arrival input is a gap distribution (an `Exponential` for a Poisson stream, or fitted); the service inputs are distributions per station;
- customers who choose among several lanes by queue length: a station group, `stations="Lane[${lanes}]:1"` with `entry="Lane"` (or `Shop>Lane:1`); each lane has its own queue and the customer joins the one with the fewest present when it joins (`ties="first"` makes the lowest lane busiest: a modelling choice to state; `ties="random"` spreads them). One station with that many servers is one shared line, a different (shorter-wait) system; random lane choice is far worse (3 lanes at 80% load: 1.28 minutes joining the shortest against 1.08 shared and 4.0 random);
- a service time that grows with an attribute (checkout time by basket, shopping time by items): `serviceScale="Lane: 0.9 + 0.1 * items"` multiplies the service input's draw (give the input a Gamma or Exponential factor of mean 1) by an expression of the attribute names; use `serviceBy` instead when each value of a category has its own distribution;
- a stage where nobody waits (shopping before checkout, a transit, a cooking time) is a delay station, `Name:inf`; entities leave it in the order their delays end, which also re-orders them for the stations after it;
- loops back (rework, readmission) are edges in `routing`;
- measure per-customer waits from `output="entities"`; measure utilization and queue length over time from the event log with the time-weighted recipe.

**Resource sets, batches and state.** `resources="Room:5, Physician:2"` and `needs="Treatment: Room + Physician"` make a service start only when a server and a unit of every listed pool are free, holding one of each; `keeps="Treatment: Room"` with `releases="Recovery: Room"` holds the room across stations (the room for the whole stay, the physician for the consultation), and leaving releases whatever is held. Stations sharing a pool are served longest-waiting first; a blocked head blocks the queue behind it. `batch="Oven: 2..4"` serves 2 to 4 entities together with one service draw. `serviceScale` may use `queue`, `busy`, `inSystem` and `size` (a load-dependent rate). Event rows then end with the free units of each pool. This replaces the old `min(rooms, physicians)` approximation: do not use that any more.

**A threshold controller with a delay** (autoscaling, a thermostat, a reorder rule on a smoothed signal) has no single primitive: assemble it in one `Recur` from three rows of this map: a reaction rule on a measured signal (average it over a window, act after a number of consecutive windows above or below a threshold), orders in flight (a state cell per delay step, or one pending order with the time left), and a stock with limits (clamp between the minimum and maximum). Keep a cooldown and whether the delay applies to removals as inputs the user can change. A piecewise-linear profile (a daily load curve) is a `Profile` node (linear, with a period) or `interp(mod(x, 24), ...)` over a clock column; a random level that changes by row multiplies it in a `Calculate`.

**Capacity, breakdowns and waiting limits.** `schedule="Runway: 0:2, 6:1, 9:2"` makes a station's servers follow the clock (shifts, weather, maintenance windows; a drop drains, 0 closes it); `breakdowns="ATM"` with inputs `up.ATM` and `down.ATM` makes each server fail and be repaired (a failure waits for the service in progress unless `breakdownMode` says `resume`, `repeat` or `lose` for the station); `timeouts="Desk: patience > exit"` (a number or an input `patience.Desk`) makes entities give up, and `timeouts="Claims: 5 > Senior"` escalates them to another station after waiting there; `timeouts="Claims: age 30 > Senior"` escalates on the claim's total age (time since it arrived, over all its stations) instead; at the escalation team, `routing="Senior[escalated=1]>back:1"` sends the claim back to the station it timed out from (`escalated` counts its timeouts so far and is never reset, so a second escalation is `escalated=2`); `queueLimit="Lane: 8 > exit"` turns arrivals away when the line is full (0 is a loss system). Rows get the types `capacity`, `down`, `up`, `timeout`, `balk` and, only when the model has a `schedule`, `poolSchedule` or `breakdowns` (not for timeouts or queue limits alone), a trailing `servers` column; utilization is then busy over the servers available, time-weighted. A counter of lost customers is the timeout and balk rows (and the `lose` rows of `breakdownMode=lose`).

**Pools on the clock, who goes first, stocks.** `poolSchedule="Runway: 0:2, 7:1, 10:2"` makes a resource pool's size follow the clock (a runway closed in bad weather; a drop drains), `contend="Landing > Takeoff"` serves the earlier station first when units come free, and `time` is a name in `serviceScale` (a service that depends on the hour). `stocks="ATM: level=50000 reorder=10000 refill=40000 delay=24"` with `uses="ATM: amount"` gives a station an amount that each service takes at its start and cannot start without; a refill is ordered when the level falls below `reorder` and arrives after the delay (or an input `restock.ATM`); the `restock` rows and a stock column show it. A service that must be cut short by a failure is `breakdownMode`. Inputs with role `entity@120` take over the entity draw from clock time 120, so a traffic mix can follow the clock. Say plainly that a lost transaction has already used its stock.

**Vehicles.** `positions` puts stations on a line (coordinates), `fleets="Car:3 capacity=8 speed=1.6 stop=4 load=1.2 dispatch=nearest"` defines cars, and `carry="Lobby>F2:Car; F2>Gate:Car"` makes those routing edges rides: the entity calls a car at the first station after its service there, waits, rides, and arrives at the second. Use it for elevators, shuttles, buses on a route, porters and AGVs on a track. Model a person who leaves by routing to a station at the same coordinate as the lobby (a `Gate`) so the model can end the trip; stations at one coordinate are one stop, so one floor can have an origin and a destination station without costing two stops. Zones are one fleet per zone with its own carried edges. A traffic mix that changes with the clock is a set of entity inputs with roles `entity` and `entity@120`, `entity@240` (the one in force at the arrival is used; `entityPeriod` repeats a day). A routing or `carry` list with hundreds of edges can be written with `@foreach` lines in the attribute (each line ending in `;`), not by a script. A dispatch rule that sounds obviously best may not be: compare the rules on the same seeds, with intervals, before recommending one. Dispatch is `nearest`, `least-loaded` or `random`; a car keeps its direction while anyone ahead needs it and turns round only at a floor, and takes over waiting calls it passes going the right way. The rows are `call`, `board` and `alight` events with the car number and its load; waits for a car are call-to-board times. Fleet options `park=Station` (idle cars go there), `redispatch=T` (a call waiting longer than T is handed to the best car then) and `board=direction` (a car takes only the calls going its way): measure them before using them; on the shipped elevator sample directional boarding was worse, parking and redispatch small gains. Not covered: loops and networks for fleets (rider-level transit over a network of lines is `network` and `transit`, below), destination dispatch with grouping, zones in one fleet, a stop plan chosen by the car beyond direction-keeping. State plainly that the dispatch rules are SpiceGrinder's, not the user's building's, when that matters.

**Transit networks (rider level, or with trains).** `network="Metro: walk=3 places=A,B,C,D,E; Red = A B C D back hop=2 stop=0.5 turn=2 headway=6; Blue = B E C loop hop=2 stop=0.5 headway=5"` declares places and lines (`back`: out and back; `loop`: one way round), the time between neighbouring places (`hop`, `hop.A-B=3` for one segment), the stop at each place passed, the turn at each end of a back line, the expected time between trains (`headway`, which may be an expression of declares, such as `24/${trains}` for a 24 minute cycle) and the walk to change trains (`walk.C=5` at one place). `ProcessFlow` works out the least-expected-time route between every pair of places when the model loads (each boarding counts half a headway of waiting, each change the walk), so a scenario that changes a headway changes the routes with no script. `transit="Gate>exit: Metro from=o to=d"` makes a routing edge a ride over the network from place `o` to place `d` (0-based, attributes or expressions of them; `To` may be a station, a group or `exit`): the entity waits a draw uniform from 0 to the headway at each boarding, rides, walks at each change, and arrives at `To`. The rows are `call`, `board` and `alight` with the network `place` and `line` (and `vehicle`, `load` as -1 and 0); entity output gains `rideWait`, `ride` and `boardings`. The route functions `routetime(o, d)`, `routelegs(o, d)` and, for leg k, `routeline`, `routeboard`, `routealight`, `routeride`, `routeheadway` `(o, d, k)` can be used in `serviceScale` and the node's other attribute expressions. The shipped subway sample (`samples/pro/process-flow-subway.xml`) is a worked example. At rider level it gives journey times and changes, not train loads: the waits at each boarding are independent draws. For loads, crowding, riders left behind and bunching give a line `trains=N` (no `headway`; it is the cycle time over N) with `capacity=C`, `load=L` (extra stop time per rider moved) and `hold=on` (keep a train at the first place until a headway has passed since the last one left); the trains start evenly spaced and run for ever, riders board in the order they came up to capacity, a rider who finds a train full is left behind (`denied` row, and a `denied` column in entity output), and one train stands at a platform at a time so trains never overtake and bunch. `depart` rows (no entity, `station` -1) carry each train's load at each place, so read loads from them. Lines with and without trains can be mixed. Routes are static on both: riders do not react to what they see. The sample `samples/pro/process-flow-subway-trains.xml` is a worked example. Not available: train breakdowns, timetables, express trains, short turns, platform capacity, routes that react to crowding; say so.

**Classes and priority.** Entities can carry numeric attributes (`attributes="class"` and an input `role="entity"`, one draw per arrival, typically a `Categorical`). `priority="ED:class"` makes a station serve the lowest value first, first come first served among equals, never interrupting a service; `serviceBy="ED:class"` with inputs `service.ED@1`, `service.ED@2`, ... gives each class its own service distribution; a routing edge may carry `[class=1]` to route by class. The attributes are appended to every output row. This covers an emergency department with triage priority, customers with different checkout times, and routing by type. Low classes can starve under load (no ageing).

`ProcessFlow` does **not** have, and the skill must not fake:
- preemption (a more urgent arrival interrupting a service in progress), ageing, or any discipline other than first come first served and priority by an attribute (shortest-job-first);
- preemption of a held resource by a higher priority (`contend` only decides who gets units that come free); a service time that depends on how late an entity is against a schedule *and* on state the clock does not give (`serviceScale` sees the attributes, the queue state and `time`); a feedback rule that reads the queue or the utilization (a controller: a `schedule` follows the clock only);
- escalation during a service (a `timeouts` entry, by wait or by `age`, applies only while the claim waits in that queue), and sending a claim back anywhere but the station it last left by a timeout (`back`; for any other return route, use attributes and conditional routing, or one escalation station per origin);
- crowd-dependent route choice on a network of lines, timetables, express or short-turn service: a `network` has static routes and trains that run its whole cycle. Journey times, routes, changes, train loads, riders left behind and bunching are `network` and `transit` (above), with no script. Say so;
- a stock that decreases over time (spoilage, leakage), shared by several stations, or refilled by a size that depends on the level; a lost transaction that returns its stock; finite queues that block the previous station; jockeying (switching lines);
- attributes that change during the stay, and conditions other than equality on one attribute;
- batch arrivals and closed networks (a fixed population circulating);
- continuous-state flows (those are `Recur` approximations).

When the system needs one of these, the options are, in order: (1) restate the question so the mechanism does not matter, and say so; (2) approximate with the nearest supported structure and state the direction and rough size of the bias (priority classes as separate `ProcessFlow`s over split capacity, for example, which is *not* the same system); (3) use `Recur` on a customer row for a hand-built rule when the line is still first come first served (a two-server shared line is in `Recur-Patterns.md`; a customer row cannot express priority, because customers then start service in a different order from the one they arrived in), or the time-step slot model below when it is not; (4) `extend-spicegrinder` for a custom component; (5) say that this part is outside what SpiceGrinder simulates.

## Slot models: resources the event engine does not have

When the rule is one `ProcessFlow` cannot express (preemption, ageing, batch service with positions, your own vehicle rule), `ProcessFlow` does not apply; resources needed together or held for different lengths, batches and vehicles on a line are in `ProcessFlow` now. The pattern that works is a time-step model whose state is the queue contents and the time left on each busy resource, kept in a `SharedState` and updated by `Calculate` nodes, one per step of the rule, with the values several columns need held in `let` locals:

- **Row** = one step, short against the service times (a minute for treatments of tens of minutes). State at the end of a row is read in the next, which is exactly "carry the state over one step", not an approximation of a feedback.
- **State cells:** the number waiting in each class (one cell per class), and for each resource slot the time left on its current job (0 when free). Slots are the units of capacity; when a job needs one of each of several resources for its whole length, the number of slots is the smallest of the resource counts, which makes the larger resource's count irrelevant to waits (say so: it is a modelling consequence the user may not intend, and an interview question).
- **One row's stages:** read the state; count down the remaining times; draw this step's arrivals per class; add them to the queues; count the free slots; give the free slots out in priority order (rank the free slots 1 to n; slot r takes the r-th waiting job counted down the classes in priority order, using the cumulative queue counts); draw the new jobs' durations; write the state back. A stage is a `Calculate` over the previous stage's columns; inside a stage, use `let` and `argmin`/`argmax`/`sum` over column ranges instead of a further node.
- **Durations** are drawn when a job starts, from the distribution of its class, rounded up to whole steps; a step of one unit shifts the service mean by about half a step, so say so and choose the step to keep that small against the service time.
- **What the output gives:** per step, counts, not people: arrivals and starts per class, number waiting per class, slots busy. Per-job waits come from a first-come-first-served reconstruction within each class, done offline from the counts (the k-th arrival of a class is the k-th start of that class), or approximately from Little's law. Say which was used.
- **Extras the user may ask for:** ageing or upgrading after a long wait (more state per queue), walk-outs (a rule that drains a queue), shifts (a capacity that follows the clock). Each is a further stage and a further assumption; ask before adding.

## Expression and configuration notes

These cost time when learned by trial:
- **Inside one `Calculate` or `Recur`, an assignment reads only the node's inputs (and, for `Recur`, the previous state), never another assignment's result.** A value that other values need is a local variable: `let t = x[0] + x[1]; y[0] = t; y[1] = t * t`. All `let`s run first, in the order written; a name must be defined before it is used and cannot be `x`, `s`, `y`, `pi` or a function name. Do not chain `Calculate` nodes to share a value.
- **Several columns at once:** `sum(x[2..21])`, `mean(...)`, `min`/`max` over a range or several values, `argmin`/`argmax` (the 0-based position of the smallest or largest, lowest on a tie), `choose(i, a, b, c, ...)` (the i-th value, as a lookup table) and a computed column `x[x[2] - 2]`. In `Recur` a range can run over the state: `argmax(s[0..5])`.
- **Many copies of a node or of a line: `foreach`, not a generator script.** A node (or an `<input>`) with `foreach="i=1..N"` becomes N copies named with the loop value (`name="Queue${i}"`), and `${i+1}`, `${i-1}`, `${i*2}` work in the copy; the bounds may use a declare (`foreach="i=1..${floors}"`). Several variables multiply out (`i=1..3, j=1..2`, last fastest). In a multi-line `expression`, the lines between `@foreach j=0..7` and `@end` are written once per value (write the line breaks as `&#10;` in an XML attribute). A repeated node's name must contain its variable. Use this before writing a script that generates XML; keep a script only for what it cannot express (data-dependent structure).
- **Many independent draws of one generator in a row:** `Replicate count="K"` over the generator (K columns, one pull each); `Redimension` is for reshaping a stream, not for this. **Many state cells:** a `SharedState` cell array `cells="q[1..20]=0"` is the cells `q1` to `q20`; `StateRead`/`StateWrite` take the same range (`cells="q[1..20]"`), and in `StateWrite` a `-` marks an input column that is not stored (`cells="q[1..6], -"`), so a value wanted only as output needs no dummy cell.
- **A `declare` is a whole attribute value (`$name`) or text inside a value (`${name}`).** A lever can sit inside an expression: `y[0] = x[0] * ${arrScale}`. Write `(${a})` where the declared text may itself be an expression.
- **Arrival rates that follow the clock:** use `RateSchedule` (time-step models) or `ProcessFlow`'s `rate` option, not a hand-built thinning. `Poisson` itself takes one constant `lambda`.
- **A `ProcessFlow` station count is literal text, not an expression.** Put the count in a `declare` and write `stations="Desk:${staff}"` (the whole-value `$name` form does not work inside a longer string). For resources that limit a station, write the station as `Name:inf` and limit it with `needs`: a delay station has no queue of its own, but with `needs` the entities do wait, for a unit of the pool (the waits in the log are not 0).
- **A run that ends at `until`:** the last event row is the last event before the horizon, not a row at the horizon, so a time-weighted average must be extended to the horizon by hand; and `output="entities"` leaves out the entities still inside unless `censored="true"`, which adds a row for each at the horizon (its age and its waits so far, `censored` 1). Without it, waits from the entity rows are biased toward the ones that finished (the lowest priority classes most). With it, report the open items' ages from the censored rows, and keep them out of plain means of completed times (or say the means include right-censored values).
- **`choose(i, a, b, c)` is 0-based** (`choose(0, a, b, c)` is `a`; an index past the list stops the run at that row; the validator's smoke test may catch it, but a smoke test cannot prove a model is free of run-time errors. Guard a computed index with `&&`: `i >= 0 && choose(i, ...)`). A table indexed by a pair is `choose(row * width + col, ...)`.
- **Combine conditions with `&&`, `||` and `!`** (each gives 1 or 0; the right side runs only when needed): `y[0] = x[0] > 0 && x[1] < 5`. In an XML attribute write `&amp;&amp;` and `&lt;`. The older product `(a>0)*(b<5)` still works but evaluates both sides, so it cannot guard a `choose` or a computed index.
- **Name the output columns** with `columns="exit, rider, journey"` on the dataset (checked at load); `grind --header` and the experiment measures then use the names instead of `c0`, `c1`, ....
- **Expressions and declares inside option strings:** `choose(...)` and the other expression functions work in `serviceScale`, and `${name}` works inside `rate`, `serviceScale`, `fleets` and the other option strings.
- **Queue length from a `ProcessFlow` event log:** use the time-weighted recipe (area under the queue column, divided by time). An arrive row shows the new entity in the queue even when it starts in the same instant, so a plain count or maximum over arrive rows overstates the queue; take peaks from start and finish rows, or from rows where every server is busy.
- **Events at one instant in a `ProcessFlow`:** a finish is processed before an arrival at the same clock time, and a hand-off from one station to the next counts as an arrival, so a finish at the next station at that instant comes first. An external arrival at exactly the `closes` time is not admitted. Write a reference simulator the same way.
- **A mean-1 Gamma factor with a declared shape:** `scale` cannot be an expression, so write `<Gamma shape="${shape}" rate="${shape}"/>` (rate equal to the shape gives mean 1); the same works with a literal number.
- **Time-weighted queue length and utilization from the events log of a station group:** it is per station. With the `experiment` command, `--by station --measure "queue=twmean(queue, time)" --measure "busy=twmean(busy, time)"` does it for every station in one call (add `--grid` and `--baseline` for lever comparisons: each station is compared with itself). By hand: for each station, the area under its `queue` column (and under `busy`) is the sum of value x (next time at that station - this time) over that station's own rows; divide by the elapsed time (and by the servers for utilization). The "customers waiting in lanes at closing" is the sum over the lane stations of the `queue` on each station's last row at or before the closing time.
- **A run that ends at a clock time:** in a `ProcessFlow`, `until="H"` ends the run at clock time H (the last events row shows the state, `inSystem` and each station's `queue`) and `closes="H"` stops arrivals at H and ends the run when the last customer has left. The model ends by itself, so any `--count` that is large enough works, and "customers still waiting at closing" is read off the events rows. In a time-step model the run is a row count: one row per step.
- **One `Recur` as the engine of a slot model.** For a big state (cars with positions, queues per floor), a single `Recur` whose expression holds many `let` statements keeps the whole step consistent: every stage sees the new values of the stage before it within the same row, with no one-row delay and no chain of nodes. Put the random draws the step may need into the `Recur`'s input (a fixed number per row: arrivals up to a cap, one draw per car), keep the clock in the state, and **generate the expression with a script** (keep the script as the readable source and say so in the model header). Echo the draws beside the state in a second copy of the model (`appendInput`), so an independent simulator can replay them row by row. Computed indexes work in the state too (`s[expression]`), as do `abs`, `mod` and `sum` of comparisons.
- **A dispatcher that assigns calls to cars every step will dither** unless the assignment is remembered: keep the assignment in the state and give a call's current car a bonus in the cost, and break ties by a fixed order, not a rotating one. Look at the maximum wait and the number never served, not just the mean.
- **When a hand-built controller is too big to trust:** past a few hundred state columns or more than one decision rule of your own invention (a dispatch cost function, a boarding rule), tell the user plainly that a custom component (`extend-spicegrinder`) is the maintainable route, state what the generated model is (a verified implementation of a written specification, not a standard algorithm), and ask whether they want the component built.
- **Scenario runs need no copy of the model:** `grind --declare lanes=6 --declare rateScale=1.2 model.xml` (repeatable) replaces declare defaults for one run; the MCP `generate` tool takes `declares`; the Service takes `?declare=name=value` at registration.
- **The model analyzer writes its results into the model file as `analysis.*` attributes by default.** Pass `--no-write` to print only, or run it on a copy.
- **XML comments cannot contain `--`.** A run command with flags (`--seed`, `--count`) breaks the load if it is written into a header comment; write it as the shipped samples do ("grind with a count of 1440 on samples/..."), and put the literal command in the report.

## Feedback and the one-row delay

All feedback through `SharedState` is delayed by one row, by design: results do not depend on where nodes sit in the model. Decide for every loop whether one row of delay is a faithful stand-in for the real delay:
- If one row is the real delay (the reorder rule sees yesterday's stock), fine, and say so.
- If the real response is immediate within the step, keep both sides inside one `Recur` or `Calculate`.
- If the real delay is longer, add the delay as a pipeline of cells (the lead time of an order) and state its length.
- If shortening the step would change the answer, the loop is sensitive to the delay; say so in the report.

## Typical systems and their shape

| System | Row | Shape |
|---|---|---|
| Inventory, one item | day | `Recur` for stock with a reorder rule, or `SharedState` when other parts read the stock. Demand `NegativeBinomial`. Lost sales or backorders is an interview question. |

| Cash runway / financial balance | month | `Recur`, with regimes by `Markov`; first-ruin as a measure (`samples/simulation/cash-runway-*`). |
| Support desk / one queue | customer | `Recur` with Lindley (`recur-lindley-queue.xml`), or `ProcessFlow` with one station. |
| Clinic / call center / checkout with several stations, first come first served | event or entity | `ProcessFlow`. |
| Emergency department with triage priority and class-dependent treatment | event or entity | `ProcessFlow` with `attributes`, `priority` and `serviceBy`. A treatment that needs a room AND a physician: `resources`, `needs`, and `keeps`/`releases` when the room is held longer than the physician. Each pool's utilization comes from the free-unit columns. |
| The same, when the room and the physician are held for different parts of the stay (a physician sees the patient briefly, the room is held for hours), or an urgent arrival may interrupt a treatment | step (a minute, say) | Slot model on `SharedState` with `Calculate` nodes and `let`; see below. |

## Experiments: levers and seeds
- **Common random numbers come free.** Every node draws from its own stream, derived from the seed and the node's name, so two runs with the same seed that differ in one lever see the same random inputs everywhere else. Compare settings with the same seeds and report paired differences.
- **A lever grid over many seeds is the `experiment` command** (`docs/Experiment.md`): `experiment --count N --seeds 30 --grid name=v1,v2 --baseline ... --measure "name=mean(c3)"` runs every setting for many seeds in process and writes means with 95 percent intervals, paired differences from a baseline on the same seeds, and proportions with Wilson intervals (only for a measure that is a proportion by its formula: a single `frac(...)`, a `mean(...)` of a comparison, or a comparison such as `max(c1) > 0`; a count or a sum gets the t interval even when its values are all 0 or 1). Define each outcome as a reducer over the output columns (`mean`, `sum`, `max`, `last`, `count`, `quantile`, `twmean` for a time-weighted mean of an event log). A probability is a 0/1 measure over paths: `--path-rows P` with the model's `resetEvery`, and a latched flag column (`max(c1) > 0`). Say how many runs or paths it was based on. Useful options: `--one-at-a-time` with a `--baseline` for a sensitivity table, several `--baseline`s, `--keep "c0 >= 24"` to drop a warm-up in time, `--by station` to get every measure per station (or per class, per hour) in one call, `--quantiles 0.05,0.5,0.95` for the spread across runs, `--pareto a:max,b:min` to mark settings no other beats on both, `--confirm "..."` to re-run chosen settings on fresh seeds, and `--format compact` or `heat:MEASURE` for a table to read.
- **`Recur`'s `initial` takes constant expressions** of numbers and declared values (`initial="${soc0} * ${C}, 0"`), evaluated when the model loads (no `s`, `x` or `y`).
- **A model that uses a `declare` is Pro**, even if every component is Free. For a Free user, a lever has to be a literal in the file (edit and re-run) or an input column.
- **A lever read inside a `Recur` expression** must be text in the expression (`${name}`), not a `Constant` node: a node's value is an input column, available through `x[k]`, only if it is wired in as an input.
- **A deterministic variant for checking** is best made by echoing the random draws into the output (`appendInput="true"` on the `Recur`) and replaying them in the reference, not by replacing them with a `Sequence`: a `Sequence` accumulates floating-point error over thousands of pulls and can flip a comparison.
- **Winner selection is biased.** The best cell of a lever grid is the best partly by luck; re-run the chosen setting and its nearest rivals on fresh seeds before recommending.
